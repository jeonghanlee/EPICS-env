# measComp TC-32 Channel Count Fix

The execution record for the measComp TC-32 thermocouple channel-count fix,
and the worked example for `docs/upstream-fix-verification-procedure.md`. A
later execution of the procedure can read it as the model for its own record:
the front-matter metadata, one section per Record-discipline row, claims
carried only where a ledger row names the evidence.

## Status

Stage 1 (compile) and the Stage 3 build steps pass on host `top` against the
latest-default tree (1.3.0); the Stage 3 hardware run is pending, and no run
on this host can replace it. Stage 2 (lab hardware) and Stages 4-6 pending.
The running production version is not owner-confirmed (see Differences and

## Defect

On Linux, `MultiFunction::MultiFunction()` in
`measCompApp/src/drvMultiFunction.cpp` takes the thermocouple channel count
from `ulAIGetInfo(AI_INFO_NUM_CHANS_BY_TYPE, AI_TC)`. uldaq 1.2.1 returns 64
for every TC-32 and E-TC32 whether or not the EXP-32 expansion board is
attached; it halves only its internal actual count when no expansion is
present, and `ulTIn` then rejects channels 32-63 with `ERR_BAD_AI_CHAN` (14).
The poller loops over `numTemperatureIn_` and calls `ulTIn` per channel, so
without the expansion it prints one error line per missing channel per cycle:

```
MultiFunction::pollerThread Error: Calling TIn, err=14 Invalid analog input channel specified
```

Temperature readings on channels 0-31 are correct; the defect is log noise,
32 lines per poll cycle on a TC-32 or E-TC32 without the expansion board.

Upstream issue epics-modules/measComp#20 (2022) raised `MAX_TEMPERATURE_IN`
to 64 but left the count at 64; commit `7b54f98` (2024-11-25, on `master`
after R4-3, the newest upstream tag) moved the thermocouple reads into the
poller. The uldaq maintainers named `ulDevGetConfig(DEV_CFG_HAS_EXP)` as the
supported expansion-detect query (mccdaq/uldaq#48); both the USB TC-32 and the
E-TC32 set the flag it reports.

## Fix

| Item | Value |
| :-- | :-- |
| Fork | `jeonghanlee/measComp` of `epics-modules/measComp` |
| Branch | `tc32-exp-chan-count` |
| Base commit | `9c8e01e`, the upstream `master` tip at branch time |
| Changed file | `measCompApp/src/drvMultiFunction.cpp` (7 lines added) |
| Code path | Linux only: the `#else` branch of the `#ifdef _WIN32` block, after the `AI_TC` channel query |
| Unchanged | the Windows path; every other board family |

After the `AI_TC` query, for `boardFamily_ == USB_TC32` (the family covers the
USB TC-32 and the Ethernet E-TC32) the constructor calls
`ulDevGetConfig(daqDeviceHandle_, DEV_CFG_HAS_EXP, 0, &infoValue)` and halves
`numTemperatureIn_` when the call returns `ERR_NO_ERROR` and the value is 0.
Any other outcome leaves the count as uldaq reported it.

## No-hardware verification

The ceiling of what host `top` can prove without an E-TC32. All against the
1.3.0 tree (`~/alsu-epics/1.3.0/debian-13/7.0.10`, base 7.0.10, asyn R4-46).

- **Compiles.** The patched module plus the environment's
  `measComp-CONFIG_MEASCOMP.p0.patch` builds `make` exit 0, no compiler
  warnings (the one build notice is the expected `CHECK_RELEASE=NO`
  release-check disable), and
  installs `cfg/CONFIG_MEASCOMP`. Evidence `work/measComp-fix/module-build-1.3.0.log`.
- **Links only to the selected tree.** `libmeasComp.so` RUNPATH names the
  1.3.0 tree and `$ORIGIN` only; `libuldaq` resolves from the tree's
  `vendor/lib`. Evidence `work/measComp-fix/readelf-1.3.0.txt`.
- **Consumer links the fix.** The tcmd IOC copy (from `git archive 17b7f51`)
  builds `make` exit 0; `ldd` shows `libmeasComp.so` from the scratch build
  and `libuldaq.so.1` from the tree `vendor/lib`; effective `ULDAQ_DIR` is the
  tree vendor prefix. Evidence `work/measComp-fix/ioc-build-1.3.0.log`.
- **Install root untouched.** `find <tree> -newer/-cnewer .started` empty.

Not provable here: that an E-TC32 without EXP-32 reports 32 channels and stops
the TIn errors. uldaq has no simulation mode and no device is attached. The
mechanism is confirmed in code (the poller bounds its `ulTIn` loop by
`numTemperatureIn_`, which the fix halves), but the device's own report is a
hardware fact - handed off below.

## Hardware hand-off

To repeat this where an E-TC32 is attached, on the production host:

1. Confirm the production version with the owner (do not assume 1.3.0; see
   Differences and next actions). Note its tree path as `<tree>`.

2. Build and verify the no-hardware part with the automation script, which
   does the scratch layout, both builds, the link checks, and the
   install-root-untouched check in one run:

   ```bash
   tools/verify_fix_stage3.bash \
     --fix-patch work/measComp-fix/tc32-exp-chan-count.patch \
     --prod-tree <tree> \
     --local-patch patch/measComp-CONFIG_MEASCOMP.p0.patch \
     --ioc-checkout /data/gitsrc/tcmd --ioc-commit 17b7f51 \
     --vendor-var ULDAQ_DIR
   ```

   It builds in `~/scratchpad/measComp-fix/` and prints the manual hardware
   steps on success. (The equivalent by-hand steps are the procedure's
   Stage 3; the script mkdir's the module dir, unpacks `9c8e01e` with
   `git -C <fork> archive`, applies the fix and the `-p0` environment patch,
   composes the config, and builds the tcmd IOC copy.)

3. In a maintenance window, run the hardware verification the script cannot:
   capture the baseline (`caget` over the 32 temperature PVs), stop the
   production IOC, start the scratch tcmd copy from its `iocBoot` with error
   output on, and check the success criteria below.

4. Teardown: stop the copy, restart the production IOC, re-read the baseline
   PVs to confirm it serves as before. The script already checked the install
   root was untouched.

## Stage 3 plan

### Success criteria

Instance: the reported unit is the E-TC32 behind `iocBoot/iocsr-tcmd`
(`SR03:E-TC1:`, port `E-TC1`, `ETC-alsu.db`). That instance carries no
`asynSetTraceMask` line, so its production log shows the noise now (per the
reporter); the two TC-32 instances (`iocar08c-tcmd1`, `iocctrlslab-tcmd`) mask
`ASYN_TRACE_ERROR` since 2026-03-10. If the run uses a masked instance, the
test copy's `asynSetTraceMask(<port>, -1, 0)` line is removed first.

- **Symptom gone.** No `Calling TIn, err=14` line over at least 10 poll cycles
  after `iocInit`, error output on. Record the `POLL_SLEEP_MS` and the wall
  time waited.
- **Mechanism confirmed.** `asynReport 1 <port>` prints
  `temperature inputs = 32`, and `ulDevGetConfig(DEV_CFG_HAS_EXP)` on the same
  unit returns 0 (from a small uldaq program built against the tree `vendor/`).
- **Unchanged behavior preserved.** Channels 0-31 read the same as the
  baseline (`caget` over the 32 temperature PVs), within normal drift.

Not covered by one unexpanded E-TC32: the with-expansion branch (must still
report 64) and the USB TC-32 variant. The upstream PR states this limit.

### Build layout

`~/scratchpad/measComp-fix/` on the production host: base source
(`git archive 9c8e01e`) + fix (`git apply` of the patch) +
`measComp-CONFIG_MEASCOMP.p0.patch`, configured by the Stage 1 table against
the confirmed tree; then the tcmd IOC from `git archive 17b7f51` with
`MEASCOMP` at the scratch module and `ULDAQ_DIR=<tree>/vendor`. `readelf -d`
and `ldd` of both are the evidence.
