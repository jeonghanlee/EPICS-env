# Release - General Procedure

The entry for a release of the EPICS-env environment. This file holds the order of a release and names, at each step, the file that holds the rule. It states a rule of its own only where no other file holds it.

- The work of this repository lives in `docs/procedures/`: one module in `module-bump-procedure.md`; the downstream patches of a module, EPICS base and pvxs included, in `upstream-fix-carry-procedure.md`; a fix that can be seen only on production hardware in `upstream-fix-verification-procedure.md`; the common iocsh fragments in `commonIocsh-verification-procedure.md`; and the rules for changing a procedure and for the reconciliation after the release in `documentation-upkeep-procedure.md`.
- Each release keeps a release record, `docs/milestone-<release>.md`: its decision log (the Decisions table), the plan and results of each module, the release plan, the lessons learned, and a History table that names the commit the record started from.
- The candidate is the commit that the checks build and test: for a module, the tip that carries its plan and any pin change; for the release, the commit that carries the release readiness evidence, which the candidate rule ties to the tip the release checks tested (step 7). A cycle is the work for one module (step 6).
- The checklist of a release, which names each check and the file that holds its rule, is `release-checklist.md`.
- The product of a release is the EPICS-env tree that the CI workflows build and the distribution ships.

A release runs bottom-up: EPICS base and pvxs, then the other modules, then the release. It reads top-down: this file, then the file each step names. The same module procedure repeats for every module.

The checks run on test machines: the local host, or virtual machines (guests) created with the public `cloud-provision` repository (Test machines, below).

## Phases

| Phase | Steps | What runs |
| :-- | :-- | :-- |
| 1. Preparation | 1 to 6 | the release branch, the survey, the reverse dependencies, the decisions, the order, the tools, and the module cycles |
| 2. Final release | 7 to 8 | the candidate, the release verification, and the merge, tag, and release |
| 3. After the release | 9 | the reconciliation, the next release branch, and the distribution products |

## Order

1. Open the release branch: `release-<release>` from master, the release record `docs/milestone-<release>.md` renamed from the `docs/milestone-<hash>.md` that master carries (the previous release handed it to master in its step 8) with a History row that names the commit that carries it, the version value `ENV_RELEASE_VERS` set in `configure/CONFIG_SITE` in the first commits of the branch, and the branch pushed to origin. The release number is set by the maintainer's dated decision that opens the branch: the patch number rises for a release of fixes only, and the minor number for a change of the module set or a feature. The GitHub milestone titled with the release number and the issue that tracks the release, titled `Verify and publish EPICS-env <release>`, are opened with the branch.
2. List the modules: every `SRC_TAG_<KEY>` of `configure/RELEASE`, `SRC_TAG_BASE` included. Each ends with one recorded outcome: IN, HOLD, or unchanged (step 4). The outcome decides only whether the pin moves; every module runs the whole cycle of step 6.
3. Survey every module and locate each pin (`module-bump-procedure.md`, Stages 1 and 2).
4. Find the reverse dependencies and judge the API/ABI compatibility of every newer upstream release (Stages 3 and 4); the maintainer decides IN or HOLD (Stage 5). Record each outcome in the decision log of the release record: an IN or a HOLD as a dated row with the module, old -> new, and a one-line reason; an unchanged module, one with no newer upstream release, which needs no decision, as a line shared by the modules that stand alike. A newer upstream release examined outside a release cycle goes to `docs/CLOSED_DOORS.md` instead. EPICS base and pvxs move in lockstep: a bump re-examines their downstream patches (`upstream-fix-carry-procedure.md`, Bump obligation). A fix that only production hardware can show is proven first by `upstream-fix-verification-procedure.md`.
5. Order all the modules: EPICS base first, pvxs next in lockstep with base (their downstream patches are examined together, and its cycle follows the cycle of base), then the dependency order of `build.<module>` in `configure/CONFIG_MODS_DEPS` from the bottom up (a module after every module its `_DEPS` lists, and modules with no order between them in the order of that file), and last the modules whose new pin carries code identical to the old pin. The order is the maintainer's dated decision in the decision log.

5a. Check the tools that every module cycle uses: read the three scripts of `tools/module-check/` and the make targets against what Stage 6 of `module-bump-procedure.md` says they do. The cycle of the first module uses the scripts as they are and works around a difference it meets by hand. Each difference is then fixed as one piece of work, with its own plan review, acceptance, commit, push, and tests on the test machines of the first module, after the cycle of the first module and before the cycle of the second, because every later cycle runs these tools. The work is recorded in the release record as an item of its own.

6. Run one cycle per module, EPICS base and pvxs included, whatever its outcome, in this order. Each commit and push has its own authorization from the maintainer, and a commit message carries the change, not the review.
   1. The issue: one per module in the release's GitHub milestone, titled with the module and the release and labelled as the issue that tracks the release, opened at the plan step.
   2. The plan, in the module's section of the release record: reviewed in two passes, one that verifies each claim of the plan against the repository and one that reads the plan from the seat of the agent who carries it out, with the findings of the passes and the maintainer's rulings recorded in the plan beside its acceptance; the maintainer accepts it and separately authorizes the implementation.
   3. The commit of the accepted plan, and, for a module whose pin is not at the decided value, the pin change and its commit (`module-bump-procedure.md`, Stage 6, step 1).
   4. The push of the candidate, the tip that carries the plan commit and any pin change, because the test machines fetch it from origin. The test machines of the cycle are prepared once, with the candidate of the first module, and carry the baseline (Test machines, below).
   5. The clean rebuild of the module and its dependents and the checks on the test machines (`module-bump-procedure.md`, Stage 6). A failure that the module or a dependent causes returns the cycle to the decision (`module-bump-procedure.md`, Rule - a failed Stage 6 returns to the decision): the new decision is a dated row of the decision log, IN or HOLD with a reason that names any downstream patch it adds, and the cycle resumes at sub-step 2 with a revised plan; Stage 6 then runs again from its step 1 (`module-bump-procedure.md`).
   6. The results in the module's section, each with its observed time, test machine, and evidence; a HOLD or unchanged module records there why its pin did not move.
   7. The commit and push of the results, with their landing on origin observed.
   8. The issue closed on the release branch, with its body synced to the results and a closing comment posted, and its closed state read back.
   9. A commit and push that record that landing and the closed issue and mark the module complete.
   10. The lessons: a rule the cycle taught goes into the procedure that owns it (`documentation-upkeep-procedure.md`, At the close of every step), and a lesson no procedure holds goes into the lessons learned of the release record, in a commit of their own after the commit that marks the module complete.
7. Prepare the release (release readiness) on the tip of the release branch after the last module cycle, pushed to origin: the integration tests re-run on the tree at that tip (the CI workflows and the Linter at that tip, the patch apply-and-revert test on a fresh checkout and the loader suite on the test machines of this step (Test machines, below) as in `module-bump-procedure.md`, The checks, items 2 and 3, with that tip as `<commit>`, an empty module argument for the apply-and-revert test, and `<sandbox>/iocsh-tests/release` as the log directory of the suite, and the common iocsh fragments by `commonIocsh-verification-procedure.md`), the version check (`ENV_RELEASE_VERS` in `configure/CONFIG_SITE` equals the release number, and `make -s print-ENV_RELEASE_VERS` prints it), the `ChangeLog.md` entry in this repository's form (`### <version> <date> <name> <email>`, the email in angle brackets as in the existing entries, dated to the day planned for the merge and tag; when the merge and tag fall on another day, only that date changes, under the candidate rule below), the README and book paths that name the release (found by a search for the previous release number over `README.md` and `docs/src`), and the production environment tests of the installed tree on the test machines of this step, for the default operating systems of the module checks or the set the maintainer extended: the tree installed at that tip, `make exist`, `make check.deps`, and `make check.env` exit 0, and, after `source $(make -s print-INSTALL_LOCATION_EPICS)/setEpicsEnv.bash` in the checkout puts the installed programs on the path, `softIocPVX` started with `exit` on its standard input exits 0; the other operating systems are covered by the CI workflows. The commit that carries the release readiness evidence is the release candidate, and the tests at that tip stand for it under the candidate rule. The candidate rule: a later commit that changes only evidence, documentation, or tools that no build or CI file references leaves the candidate valid once the comparison of its inputs with the tested source is recorded; any other change reopens the checks it maps to. A workflow that ignores documentation-only pushes has no run at a documentation-only candidate; its run at the last commit that changes code stands, once that comparison is recorded.
8. Write the release plan in the release record, one row for each action of this step, with the commits and pushes around them, and one for the branch deletion of step 9 when the plan carries it, each with its command in full, its authorization, and its expected result, and have the maintainer accept it. A value that exists only when the row runs, such as a commit hash or the files of a commit, is a placeholder in the command and is filled in when the row is shown for its authorization. Then execute and verify the release with its rows, each row with its own authorization and followed by a commit that records its result: on the release branch before the merge, and on master after it. The push of the result commits of the release branch before the merge is a row of its own, so that the merge takes a tip that origin holds. The result of that push is recorded on master after the merge, because a result commit on the release branch would need another push. Before the merge, local master is brought up to date with origin by a fast-forward, and the release branch contains it: `git rev-list --count release-<release>..master` prints 0. The merge into master, the annotated tag, the push of master, the push of the tag, and the creation of the GitHub release of the tag are separate rows. The annotated tag names the merge commit, because a result commit of the merge row can follow it and the tip of master is then another commit. The notes of the GitHub release are written from the `ChangeLog.md` entry of the release, in the form of the notes of the previous release (`gh release view <previous-release> --json body --jq .body` prints them), and are shown to the maintainer before the row. The merge takes the tip of the release branch after the last result commit before the merge, not the candidate, and the comparison of that tip with the candidate is recorded under the candidate rule of step 7. The release objects are then observed with their identifiers: the tag on origin peels to the merge commit, and the GitHub release of the tag is published. The issue that tracks the release itself closes after the release objects exist, with its body synced to the results of the rows and a closing comment that names the tag, the merge commit, and the GitHub release, unlike a module issue, which closes on the release branch; the release's milestone then closes, and every issue linked to it is read back in its final state. At the close the release record is handed to master as the starting record of the next release: a commit on master renames `docs/milestone-<release>.md` to `docs/milestone-<hash>.md`, where `<hash>` is the short hash of the commit that carries the closed record, keeps only the work that survives the release (the Deferred work, and each module or work row that is not complete, with the decisions those rows cite), and adds a History row with the full hash of that commit and the date. The result commits on master and this handover commit are pushed in the final row. The results of the handover and of the final push are not committed, because the record is already handed over; the closed record keeps them `pending`. The closed record is read at that commit, with `git show <commit>:docs/milestone-<release>.md`.
9. After the release: the procedures of this repository and the archive are reconciled in one pass (`documentation-upkeep-procedure.md`, After the release). The maintainer deletes the release branch of the release before the previous one, locally and on origin, once its tag is on origin and it is merged, since the tag keeps its content; a row of the release plan may carry the deletion as soon as the release objects exist. The next release branch opens by a separate dated decision, and the distribution products are built from the released tag outside this repository.

## Test machines

The module checks run on one test machine for each operating system of the release: by default Debian 13 and Rocky Linux 8.10. At the start of a release the maintainer may extend the set by a dated decision (Debian 12, Debian 14 once it exists, Rocky Linux 9 and 10, Ubuntu 24.04 and 26.04); a module that reopens the Ubuntu 26 C17 question uses an Ubuntu 26.04 machine. A test machine is either the local host, for its own operating system, or a virtual machine (guest) created with the public `cloud-provision` repository for an operating system the local host does not cover. Either kind is new, or already deployed with the tree installed again from nothing after its sandbox checkout `<sandbox>/EPICS-env` and its install location `<sandbox>/epics` are removed; the second saves time and resources, and it is the only way on a physical machine such as the local host, which cannot be recreated. Ask the maintainer for the guests once per release, with the candidate of the first module, and state the purpose, the operating systems, the resources (vCPU, memory, and disk as values, those of the previous release's guests unless the build needs more; record the values used), the duration (the end of the module checks), whether they are new or already deployed, that their disks are kept as evidence until the results are recorded, and who connects to them. Step 7 prepares its own test machines the same way. Tell the maintainer when the release no longer needs the guests.

On the local host, run the commands directly. Connect to a guest over SSH as the user the maintainer names, with `-o ControlMaster=no -o ControlPath=none`, and `-o StrictHostKeyChecking=accept-new` for a new guest. On each test machine, check the tools of the loader suite with `command -v gawk expect strace socat podman shellcheck` and install the missing ones: `sudo apt-get install -y gawk expect strace socat podman shellcheck` on Debian; `sudo dnf install -y epel-release` and then `sudo dnf install -y gawk expect strace socat podman ShellCheck` on Rocky Linux. A test machine needs a writable `/tmp` with free inodes, because EPICS base writes a temporary file there with `antelope` and ignores `TMPDIR` (check `df -i /tmp` before any build and require free inodes in the thousands), and disk for the loader suite, which writes several gigabytes for each run that is kept.

The baseline is the whole tree built once per release at the candidate commit of EPICS base, the first module, and again at the current candidate only when a failed loader suite has damaged it (`module-bump-procedure.md`, The checks, item 3), as the fixed environment that every module cycle rebuilds into (`module-bump-procedure.md`, Stage 6). Build it on each test machine in a sandbox in the home of the user who runs the checks: `<sandbox>` is `~/sandbox` unless the maintainer names another place; ask the maintainer at the start when it is not given, never create it under `/opt`, and write it as `readlink -f` prints it. Clone this repository (`https://github.com/jeonghanlee/EPICS-env`) into `<sandbox>/EPICS-env`, check out the candidate, set the install location inside the sandbox (`INSTALL_LOCATION=<sandbox>/epics` in `configure/CONFIG_SITE.local`; `docs/src/procedures/choose-install-location.md`) so that the user owns the tree and make never falls back to `sudo`, and build step by step as `docs/src/procedures/build-and-install.md` sets out, with the vendor libraries uldaq and open62541 built first when `/usr/local/lib` lacks them (the check of that page). On a Debian 13 host with 8 cores the baseline takes about 25 minutes: about 3 for the vendor libraries, 1 for `make init`, 2 for `make patch`, `make conf`, and `make check.module-deps`, and 18 for `make build`, `make install`, and `make symlinks`. The baseline is good when `make exist`, `make check.deps`, and `make check.env` exit 0 and `git -C <sandbox>/EPICS-env rev-parse HEAD` prints the candidate; record the OS point release, the kernel, the compiler, and the count of the entries of the installed `modules` directory with `cat /etc/os-release` (and `cat /etc/debian_version`, which holds the point release, on Debian), `uname -r`, `gcc --version`, and, in the checkout, `find $(make -s print-INSTALL_LOCATION_EPICS)/modules -mindepth 1 -maxdepth 1 | wc -l`, the count that `module-bump-procedure.md`, The checks, item 3 compares after a failed loader suite; in a release these facts go into the release record, and outside a release into the report of the work that built the tree. The test machines of step 7 install the tree at the tip that step 7 tests the same way, and `git -C <sandbox>/EPICS-env rev-parse HEAD` then prints that tip.
